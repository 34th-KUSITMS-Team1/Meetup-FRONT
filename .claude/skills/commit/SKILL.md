# 커밋 메시지 제안

## 현재 변경

- 파일: !`git status --short`
- staged: !`git diff --staged --stat`

## 순서

1. 범위를 정합니다. 인자가 있으면 그 범위만, staged 변경이 있으면 staged만, 없으면 전체 변경을 봅니다.
2. `git diff`(staged면 `--staged`)로 실제 내용을 읽습니다. 파일명만 보고 판단하지 않습니다.
3. 아래 커밋 컨벤션을 적용합니다.
4. 서로 독립적인 목적이 섞여 있으면 커밋을 나눠 제안합니다. 예: 기능 코드와 `app.json`/의존성 변경.
5. 커밋마다 `커밋 N: <type>: <subject>` 한 줄과 포함할 파일 목록을 보여주고, 그 커밋을 만드는 `git add`와 `git commit -m` 명령을 함께 적습니다.

## 커밋 컨벤션

형식은 `<type>: <subject>` 한 줄입니다. scope는 쓰지 않습니다. `.husky/commit-msg`가 형식과 AI 출처 문구를 검사하므로, 여기를 바꾸면 그 파일도 함께 고칩니다.

| type | 용도 |
| --- | --- |
| `feat` | 사용자에게 보이는 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서, 주석, README, AI 지침 |
| `style` | 포맷팅처럼 동작에 영향 없는 변경 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `test` | 테스트 추가/수정 |
| `chore` | 설정, 빌드, 의존성 |

- subject는 한국어 명령형 또는 명사형으로 50자 이내, 마침표 없이 씁니다.
- 무엇을 했는지보다 왜 바꿨는지가 드러나게 쓰고, 파일명을 나열하지 않습니다.
- 예: `feat: 배달 추적 Live Activity 시작`, `chore: expo-widgets 설정 추가`, `fix: 송금 앱 복귀 후 확인창 미표시 수정`

## 지키는 것

- 사용자가 커밋 실행을 명시적으로 요청한 경우에만 `git add`/`git commit`을 실행합니다.
- AI 출처 문구(`Co-Authored-By`, `Generated by`)를 넣지 않습니다.
- lint, 타입 체크 등 검증하지 않은 변경이 있으면 커밋 전에 확인할 항목으로 따로 적습니다.
- `.env*`, `.claude/settings.local.json`처럼 공유하면 안 되는 파일이 포함되면 제외하라고 알립니다.
